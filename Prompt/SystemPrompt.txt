ESCOPO Macro

Vamos iniciar um projeto diferente hoje.

Voltado para minha área de TI em desenvolvimento e sustentação de software.

Vamos desenvolver uma plataforma para gestão das demandas de desenvolvimento com:

1 - inclusão de novas Features
2 - Integrações com outros sistemas internos
3 - Integrações com outros sistemas de clientes
4 - Integrações com outros sistemas de fornecedores
5 - Automatizações de processo dentro de sistemas
6 - Automatizações de processos manuais com planilhas
7 - Melhorias de Features já existentes nos sistemas
8 - Alteração de Features já existentes nos sistemas

A ideia é montar um modelo hibrido com Agile Scrum, RUP com documentação UML para análise e estimativa de esforço com User Case Point e ITIL para gestão com GMUD, priorização, evidências de homologação e controle de Realease e caso necessário RollBack.

INICIO DO PROCESSO FASE 1

Toda nova demanda deve ter o solicitante, qual sistema e versão, área solicitante, Operações/Plataforma/Contratante (Um ou mais)

Toda demanda vai ter um código com o prefixo DDev seguido do ano com 4 digitos e um sequencial de 8 digitos permitindo até 10 milhões de demandas por ano. Exemplo a quadragésima quinta demanda aberta no ano de 2026 será DDev20260000045

Toda demanda deve ter em usa abertura os dados a serem preenchidos conforme o arquivo template 1 - Template - Demanda de desenvolvimento.pptx

Após a abertura demanda deve ser aprovada e ter a prioridade definida pelo aprovador. Neste momento deve-se registrar a data e hora de aprovação

Aprovador deve ter uma tela para consulta com todas as Demandas pendentes de aprovação para sua área e ter filtros que permitam a ele consultar as demandas já aprovadas ou rejeitadas e suas respectivas etapas e Leadtime de passagem em cada uma delas

Após aprovada a demanda ela volta para o demandante executar o preenchimento do Requisito de Negócio e Caso de Uso Macro.

Uma demanda rejeitada deve ter a data e hora de rejeição e solicitar ao aprovador o motivo da rejeição - Aqui é necessário um agente de IA que faça a análise do motivo de rejeição indicando se o motivo informado está adequado a demanda colocada. Exemplo de motivo de rejeição adequado:  Demanda de Criação de Relatório para Controle de Equipamento - Rejeitado - Motivo Rejeição: Utilizar a Aplicação para controle de equipamento Exemplo de motivo de rejeição inadequado. Demanda: Cria tela para informar serial do equipamento e trazer histórico. Rejeitado. Motivo da Rejeição: Eu não quero


FASE 2

A Etapa 2 deve ter todas as informações necessárias conforme o arquivo template 2 - RNUC - Requisitos de Negócios - Users Cases Macro.docx

A Etapa 2 permite revisão registrando as alterações entre uma revisão e outra e após esse processo passar por aprovação

O aprovador deve ter uma tela com todas os Requisitos de Negócios - Users Cases Macros pendentes de aprovação e ao aprovar registrar a data e hora de aprovação teve permitir ainda a consulta de Requisitos de Negócios e Users Case Aprovados ou rejeitados anteriormente sendo que Requisitos de Negócios e User Cases Rejeitados voltam para o demandante para uma nova revisão e envio para aprovação

Vamos precisar de um agente de IA para as etapas 1, 2 e 3 seja validando ou ajudando o demandante a escrever a Demanda, os Casos de Usos, as Users Stories e com Machine Learnig com conhecimento dos sistemas e negócio e questionando as necessidades solicitadas com possíveis GAP ou inconsistências do negócio com as Respectivas Regras de Negócio e Critérios de Aceite

Após aprovada a demanda vai pro time de TI definir que analista dará sequimento
